Safety

Safety by design

What EA-bot and its crew may do on their own, what waits for me, and what they never do. In plain words, and honest about which limits are scripts and which are only rules.

Ashish Raina2 Nov 2026

A good contractor can use the tools on site without asking. They ask before they knock down a wall. And some things they never do, whoever asks. My agents work the same way.

What the crew does on its own

  • Reads files and writes code, but only in a throwaway copy of the repo, one copy per task. My own copy is never touched.
  • Runs tests, linters and a browser to check its own work.
  • Researches, and writes reports and drafts for me to read.
  • Pushes its own branch and opens a pull request for review.

What waits for me

  • Merge. A pull request goes into the main branch only when the merge authority says so. Workers never merge.
  • Push to main. Workers push only their own branch.
  • Delete. Deleting data, rewriting history, force-pushing, uninstalling. A vague reply is not approval.
  • Money. Anything that spends money or changes an account.
  • Anything that leaves the machine. A post, an email, a message. Agents write drafts; I send.
  • New rules for the agents. They propose rule changes with evidence. I approve each one (see Your corrections are your next rules).

What it never does

  • Put secrets (keys, tokens, passwords) in files, commits, logs or prompts.
  • Send, post or publish without my OK.
  • Edit its own rules.
  • Hand work to hidden helper agents from the orchestrator, where no one can see or supervise it.

Which limits are scripts, and which are only words

A rule in a text file is a request. A script is a lock. I call a rule with no script behind it "begging" (from the talk in Guides and sensors). Here is which is which.

The "rule only" rows mostly hold. But a rule is not a lock, and I say so here rather than pretend. Moving rules into scripts is the work in Guides and sensors, section 10.

False passes

A false pass is work that passed every check, and that I still rejected. On 2 November I logged 9 of them.

I log them on purpose. Each one is a gap between what my checks test and what I meant. The work met the letter of the checks, not the intent. That is the alignment problem in small. When the same kind of false pass comes back, the fix is a new guide or a new sensor, not more trust.

Checks that proved me wrong

A claim is worth only the check behind it. Two checks found my setup wrong, and both stay on the site on purpose.

  • A plain-English rule broke a test. Scouts now run a plain-English checker before they say "done". That checker lives in my context system, and a test says the supervisor must never point back at it. The test now fails, 36 pass and 1 fail. I keep the failing test, because it reports a real trade-off.
  • "Scouts run with permission checks on" was false. An earlier manual said so. A check counted the flags on the running workers: all 10 skipped the checks. Skipping is the standing default, and the manual now says so.

The pattern: write the claim down, name the check that would prove it, run it, and keep the result even when it is bad. Until a check passes, the claim is "in trial", never a feature.

What this page does not claim

  • This is one person's setup, not a product. The agents run on my own machines with my own accounts.
  • A bug in a script, or a rule an agent misses, can still get through. This page lists the limits that exist. It is not a security audit.
  • Most of the machinery is Kun Chen's open-source FirstMate and no-mistakes. The rules and the choices are mine.
