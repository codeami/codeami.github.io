The idea: a library for your AI

The idea in one line

Turn what you know into folders of plain files. The AI then works like a librarian: it checks the index, fetches only the books a task needs, and reads them at its desk.

What each thing is

Where "everything is a file" comes from

Unix, the system under Macs and most servers, treats nearly everything as a file you can open: your disk, your keyboard, even a running program. One plain rule made a complicated machine easy to use. This post borrows the rule for your own life: put it in plain files and folders.

PrincipleOne folder per kind of work, one index at the top, and the AI opens only what the task needs.

03

Your first five minutes

Build the smallest library

  1. Make a folder called my-life.
  2. Inside it, make a text file named AGENTS.md. This is your map. Write a few lines: who you are and how you like answers.
  3. Make one folder for something you work on, such as money, and put one file in it, CONTEXT.md: a few lines on how that work is done.
  4. Start your next chat with: "Read my-life/AGENTS.md first."

What goes in the map

  • Who you are, in one line.
  • How you like answers: short, plain, no hype.
  • For money questions, read money/.
  • For anything else, ask which drawer.

Why that file name

Many AI tools look for AGENTS.md by name and read it when a session starts. If yours does not, the line in step 4 does the same job.

PrincipleStart with one map and one drawer. Add a drawer only when you need it.

Drawers and the card catalogue

The filing cabinet: one room each

Each kind of work gets its own folder, a room. A CONTEXT.md inside says how that work is done: the tone, the template, what to check. My blog room also holds a tone file and a template for how a post is laid out.

The card catalogue: the map

At the top sits one short file, AGENTS.md. It holds who you are, your house rules and a routing table: for this task, open this drawer.

The reading desk

Library and desk

Your folders hold thousands of books. The AI's context window is the desk: it knows only what is open on it right now. A file in a folder does nothing until the librarian opens it.

Two ways to check what was opened

  1. A canary. Put a nonsense line in the map, such as ctx-canary: blue-teapot-42, and ask the AI for it. If it answers, the map was read.
  2. A "files read" list. At the end of every task, the AI names the files it actually opened.

Instructions and material

Your rules on the desk are instructions. A web page or document the AI opens is material to work with, and it does not give orders.

The full post

For readers who want the whole argument

The problem: every chat starts from zero

You open a new chat and explain yourself again: who you are, what you are working on, how you like things done. When the chat ends, the AI forgets all of it. What you know about your own life sits in notes apps, email, old chats and your head, where no AI can see it.

So you retype the same background every time, and the AI fills the gaps with guesses. You ask for one thing and get a confident answer to a different question. A cleverer prompt does not fix that. What fixes it is a place to keep what you know, written once, that every AI tool can read.

The idea: a library for your AI

Think of a library. Your folders are the library: thousands of books, most of them closed. The AI is the librarian. A good librarian does not carry every book to your desk. They check the card catalogue, open the one drawer your question needs, and put a few books on the reading desk. Your folders are the library; the AI is the librarian, and only a few books reach its desk.

  • The library is all your folders.
  • The filing cabinet is one room: a folder for one kind of work, with a file saying how that work is done.
  • The card catalogue is the map: one short file that says which drawer to open for which task.
  • The reading desk is the AI's context window, the few files it has open right now.
  • The librarian is the AI tool: Claude, Codex, Gemini or whichever you use.

This page's address, everything-is-a-file, comes from an old idea in Unix, the system under Macs and most servers. Unix treats nearly everything as a file you can read and write: your disk, your keyboard, even a running program. That one rule made a complicated machine simple to work with. Working with AI is heading the same way. Jake Van Clief calls his version the Interpretable Context Methodology (ICM): stop pasting the same explanations into chats, write them down as plain files in folders, and let the AI read the ones it needs.

Your first five minutes

You do not need a system to begin. You need one folder and one file.

  1. Make a folder called my-life.
  2. Inside it, make a text file named AGENTS.md. This is your map, the card catalogue. Many AI tools look for that exact name and read it when a session starts.
  3. Make one folder for something you work on, such as money, and put one file in it, CONTEXT.md, with a few lines on how that work is done.
  4. Start your next chat with: "Read my-life/AGENTS.md first." If your tool reads AGENTS.md by itself, this line is optional. If it does not, the line does the job.

A first map can be this short. It is a made-up example:

Who I am: Sam, a teacher learning to use AI.
How I like answers: short, plain, no hype.

For this kind of task, open this drawer:
- money questions   → money/CONTEXT.md
- lesson planning   → teaching/CONTEXT.md
- anything else     → ask me which drawer

Add a drawer when a kind of work keeps coming up, not before.

Drawers and the card catalogue

A good AI library has three kinds of file:

  • The map: one short file at the top, AGENTS.md. Who you are, your house rules, and a table: for this kind of task, go to this drawer and read these files.
  • The rooms: one folder per kind of work, each with a CONTEXT.md that explains how that work is done.
  • The tools: scripts and skills the rooms can use, once you have some.

This is the shape of a small library:

my-life/
├── AGENTS.md          the map: who I am, my rules, the routing table
├── money/
│   └── CONTEXT.md     how I handle money
├── health/
│   └── CONTEXT.md     how I track health
└── writing/
    ├── CONTEXT.md     how I write
    └── voice.md       my tone, saved once

And this is the kind of routing table inside the map:

| Task                      | Open drawer   | Read first            |
|---------------------------|---------------|-----------------------|
| Write or edit a post      | writing/      | CONTEXT.md, voice.md  |
| Money question            | money/        | CONTEXT.md            |
| Anything else             | ask which drawer           |

The routing table is the most important part. Without it, the librarian either pulls every book off the shelf (slow and expensive) or guesses which one you meant.

A card that points to a shelf that has moved is a real failure for AI tools too: When the notes are wrong.

The reading desk

A file on disk is not something the AI knows. The library holds thousands of books. The AI knows only what is open on its desk right now, and a file in a folder does nothing until the librarian opens it. The name CONTEXT.md does not make it load by magic.

folder (library)          context window (desk)
─────────────────         ─────────────────────
AGENTS.md          ──►    AGENTS.md        ✓ loaded at the start
writing/CONTEXT.md ──►    CONTEXT.md       ✓ read, because the route said so
money/CONTEXT.md          (not read)       ✗ not needed for this task

So check what the AI actually read. There are two ways:

  1. A canary. A canary is a test line that proves a file was read. My map contains a nonsense line, ctx-canary: blue-teapot-42. If I ask an AI for the canary and it answers correctly, the map loaded. If it cannot, it did not, however sure the setup looks.
  2. A "files read" list. One house rule: at the end of every task, list the files you actually read.

Not everything on the desk is equally trusted. My rules are instructions. A web page or document the AI opened is material to work with, and it does not get to give orders.

Three habits that keep it working

Because every tool reads the same map at the start of a session, the map is also where the lessons from each session should end up. Three habits make that work:

  1. Say feedback as a rule. Not just "redo it", but "too formal, keep my conversational tone". The AI can only save what you actually said.
  2. Declare the end. "End of session" tells the AI to write its notes: the goals, constraints and decisions, where it went its own way, and which files it read. Close the tab without saying it and the lesson is gone.
  3. Keep the map yours. Sessions write notes into an inbox folder, never into the map. A small open-source tool, Kun Chen's backpass, reads those notes and proposes a rule only when the same correction shows up in at least two sessions. I go through the proposals one at a time and approve what is right. The map changes only with my OK.
start   → the tool loads the map (+ the room's CONTEXT.md)
during  → you give feedback and constraints out loud
end     → you say "end of session"; the AI writes notes to the inbox
daily   → a tool reads the notes and proposes rule changes
review  → you approve or reject; only approved rules go into the map

Keep the index card

In Jake Van Clief's video "You're Automating The Wrong Layer", someone asks a model to tighten a paragraph. It takes four rounds:

"too wordy"                      → goal: shorter
"weirdly formal now"             → keep my rhythm
"think Vox, not the FT"          → general audience
"more measured — like this one"  → measured, not casual + an example

Nobody set out to write a style guide, but by round four there is one, scattered across the chat. Save the decisions as a file (writing/voice.md in the library above) and next time "tighten this paragraph" is right in one go. I turned a week of my own corrections into rules the same way, in Turn your corrections into rules your AI follows.

When an answer comes back wrong, change one thing and rerun:

read → draft → check against the source → find the one cause → change one line → rerun the same task

Keep the change if it helped. Drop it if it did not. One change, one visible effect.

One map, any librarian

One map, linked into every tool

Every AI tool looks for its own instructions file in its own hidden folder in your home folder. Claude Code reads .claude/CLAUDE.md, Codex reads .codex/AGENTS.md, Gemini reads .gemini/GEMINI.md. Left alone, you end up with copies that slowly disagree.

Unix people solved this long ago with dotfiles: keep all those hidden settings files (the ones whose names start with a dot) in one git repository, and put a symlink where each tool expects its file. A symlink is a shortcut: the tool opens its own file and lands on the real one.

.claude/CLAUDE.md           ─┐
.codex/AGENTS.md            ─┤
.config/opencode/AGENTS.md  ─┼──►  dotfiles/home/AGENTS.md   (the one real file)
.gemini/GEMINI.md           ─┘

Change one file and every tool sees the change from its next session. I borrowed this setup from Kun Chen's dotfiles, which manage the links with Nix. There are two limits. Links only help tools that read files from your disk, so for chat apps such as Claude.ai you paste the map into a project. And each machine needs its own copy of the repository.

Swap the librarian

The AI model is one step in the middle. Around it sit plain code, written rules and checks.

request → routing → tools → model → check → result
           code      code    (swap)  person + code

The useful question is: if I changed the model tomorrow, what would still work? In my setup, almost everything. The map is the written rules, the checks run in code, and Claude, Codex or Pi is whichever librarian is at the desk. The same setup runs several coding agents side by side through Kun Chen's FirstMate, and each one reads the same map through its own tool's link.

When the library gets huge

This plain method is built for one person's library. A company's document store outgrows what fits on one desk. Those setups add a search index, known as RAG (retrieval-augmented generation), which finds the right pages and hands them to the AI. When your own files outgrow the desk, that is the next step.

Next, I plan to add a small MCP server with two tools, "load context" and "save context". MCP is a standard way for apps to call tools, and this one would let chat apps such as Claude.ai read the map and write to the inbox too.

Why it matters

A diary does two jobs. It helps you sort out your week, and years later it is the record you reach for. Folders of notes work the same way, and now an AI can read them too.

Expressing yourself, journaling and taking notes build a record that helps you. The same record means the AI works your way, with no re-explaining. It also gives someone new to AI a place to start: their own notes, not a blank page. From there they can go on to contribute to the bigger good.

If you take one thing from this post, take this. Write down what you keep explaining. Put it where every tool can find it. Change it only on purpose. Then build the smallest library: one folder, one map file, five minutes.
