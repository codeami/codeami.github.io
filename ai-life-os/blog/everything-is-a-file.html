The full post

For readers who want the whole argument

Unix has an old idea: everything is a file. Your keyboard, your disk, even a running program show up as files you can read and write. It made a complicated machine simple to work with.

Working with AI is heading the same way. Jake Van Clief calls his version the Interpretable Context Methodology (ICM). Strip away the name and it says this: stop pasting the same explanations into chats. Write them down as plain files in folders, and let the AI read the ones it needs.

This post walks through how I set that up. I built a small working version as I went, and each section ends with a test that checks it.

1. Three levels of using AI

Think of cooking.

  • Level 1, the recipe card. You read a recipe off your phone, cook, and forget it. Next time you look it up again.
  • Level 2, your own recipe book. You've written down how you make it: less salt, a bit more garlic, the pan you like. It comes out right the first time.
  • Level 3, a kitchen. Ingredients sit where you expect them. Your recipe books are on the shelf. Anyone in your kitchen can cook your dishes.

AI works the same way. The jump from level 1 to level 2 is simple: save what worked as a file. Level 3 is when you organise those files so the AI can find them on its own. That's where the payoff is:

  • It works without you in the room. A fresh AI session, or a different AI tool, reads the same files and works your way. No re-explaining.
  • Many cooks at once. In my setup FirstMate runs several coding agents side by side, and they all read the same base file.
  • Fix it once, fixed everywhere. Correct a rule in one file and every tool picks it up from the next session.
  • Cheaper. The AI reads only the files the task needs, instead of a giant prompt pasted every time.
  • It gets better. Session notes turn into better rules (section 2).
  • You can hand it over. Give someone, or another AI tool, the folder and they can work.

The catch: a kitchen takes some setting up, and a messy kitchen is worse than a recipe card. That's why the next sections are about keeping it small and tidy.

level 1:  chat ──► answer ──► (forgotten)
level 2:  chat + voice.md ──► better answer
level 3:  folder (map + rooms + tools) ──► agent finds what it needs

Test: tests/run.sh section S1 checks that every kind of work I do has a written process (CONTEXT.md), and that the blog room has its saved tone guide (voice.md) and template.

2. Map, rooms and tools

Walk into any office building and there's a floor plan by the lifts. It doesn't tell you how to do your job. It tells you which floor to go to.

A good AI folder has three kinds of file:

  • The map: one short file at the top (AGENTS.md). Who I am, my house rules, and a table: for this kind of task, go to this folder and read these files.
  • The rooms: one folder per kind of work, each with a CONTEXT.md that explains how that work is done.
  • The tools: skills and scripts the rooms can use.

This is the shape of the folder I use. It lives in my dotfiles repo:

dotfiles/
├── home/AGENTS.md        the map: who, rules, routing table
├── context/              the shared agent context
│   ├── areas/            one room per kind of work:
│   │                     blog, factory, cert-prep, content, harness …
│   ├── inbox/sessions/   what each AI session leaves behind
│   └── tests/            run.sh · e2e-probe.sh
└── home.nix              the list of links (see below)

And this is the kind of routing table inside the map:

| Task                      | Go to            | Read first            |
|---------------------------|------------------|-----------------------|
| Write or edit a blog post | areas/blog/      | CONTEXT.md, voice.md  |
| Software factory work     | areas/factory/   | CONTEXT.md            |
| Cert prep                 | areas/cert-prep/ | CONTEXT.md            |
| Anything else             | ask which room   | —                     |

The routing table is the most important part. Without it, the AI either reads everything (slow and expensive) or guesses.

The key trick: one file, linked into every tool

Every AI tool looks for its own instructions file in its own hidden folder in your home folder. Claude Code reads .claude/CLAUDE.md, Codex reads .codex/AGENTS.md, Gemini reads .gemini/GEMINI.md. Left alone, you end up with four copies that slowly disagree.

Unix people solved this long ago with dotfiles. Keep all those hidden config files (the ones whose names start with a dot) in one git repo. Then put a symlink where each tool expects its file. A symlink is a signpost: the tool opens its own file and lands on the real one in your repo.

.claude/CLAUDE.md           ─┐
.codex/AGENTS.md            ─┤
.config/opencode/AGENTS.md  ─┼──►  dotfiles/home/AGENTS.md   (the one real file)
.gemini/GEMINI.md           ─┤
.agents/AGENTS.md           ─┘   (for backpass)

Change one file and every tool sees the change from its next session. New laptop? Clone the repo, run one script, and the signposts come back. I borrowed this setup from Kun Chen's dotfiles, which manage the links with Nix.

There are two limits. Links only help tools that read files from your disk. Chat apps like Claude.ai can't, so there you paste the map into a project. And each machine needs its own copy of the repo.

Load it at the start, save at the end

Because every tool reads the same file when a session starts, it's also where the lessons from each session should end up. Think of a hospital shift change: the incoming nurse reads the patient's chart, the outgoing nurse writes down what happened. Same chart for every nurse, and nothing depends on anyone's memory.

start   → the tool loads the map (+ the room's CONTEXT.md)
during  → you give feedback and constraints out loud
end     → you say "end of session"; the AI writes notes to inbox/
daily   → backpass reads the session logs and proposes rule changes
review  → you approve or reject; only approved rules go into the map

Three habits make this work:

  1. Say feedback as a rule. Not just "redo it", but "too formal, keep my conversational tone". The AI can only save what you actually said.
  2. Declare the end. "End of session" tells the AI to write its notes: the goals, constraints and decisions, where it went its own way, and which files it read. Close the tab without it and the lesson is gone.
  3. Never let a session edit the shared file. Notes go into inbox/, not into the map. Kun Chen's backpass reads the session logs and proposes a rule only when the same correction shows up in at least two sessions, with exact quotes as proof. I go through the proposals one at a time and approve what is right. The map only changes with my OK, so it stays a rulebook I agreed to.

Test: tests/run.sh section S2 checks that the map has a routing table with a fallback row, that every file the table names exists, and that home.nix links Claude, Codex, OpenCode and Gemini to the one map. Section S3 checks that the map says what to do on "end of session" and routes rule changes through backpass.

An honest note: S2 also checks the map is short, at 120 lines or fewer. On 2 November my copy is 133 lines, so that check fails until I trim it. The map grows one reasonable rule at a time. The test is there to catch exactly that.

3. A file on disk is not something the AI knows

Think of a library and your desk. The library has thousands of books. You only know what's in the three books open on your desk right now.

Your folders are the library. The AI's context window is the desk. A file sitting in a folder does nothing until the AI actually opens it. The name CONTEXT.md doesn't make it load by magic.

folder (library)          context window (desk)
─────────────────         ─────────────────────
AGENTS.md          ──►    AGENTS.md        ✓ loaded at start
areas/blog/...     ──►    CONTEXT.md       ✓ read because the route said so
areas/factory/...         (not read)       ✗ not needed for this task

So you need a way to check what the AI actually read. I use two:

  1. A canary. My map contains a nonsense line, ctx-canary: blue-teapot-42. If I ask an AI for the canary and it answers correctly, I know the map really loaded. If it doesn't, it didn't, however sure the setup looks.
  2. A "files read" list. One house rule: at the end of every task, list the files you actually read.

There's a second half to this. What's on the desk isn't all equally trusted. My rules are instructions. A web page or document the AI opened is just material to work with, and it doesn't get to give orders.

Test: tests/run.sh section S3 checks the canary is in the map. tests/e2e-probe.sh is the real end-to-end test: from an empty folder it asks Claude Code, Codex, Gemini CLI and OpenCode for the canary. A tool passes only if the map actually reached it.

4. Every workflow starts as a conversation

A good tailor writes your fit notes on a card: likes room in the shoulders, hates a tight waist. The next suit fits first time. Most of us use AI like a tailor with no card. We go round and round in a chat until it's right, then close the tab and lose everything we just taught it.

In Jake's video "You're Automating The Wrong Layer", someone asks a model to tighten a paragraph. It takes four rounds:

"too wordy"                      → goal: shorter
"weirdly formal now"             → keep my rhythm
"think Vox, not the FT"          → general audience
"more measured — like this one"  → measured, not casual + an example

Nobody set out to write a style guide, but by round four there is one, scattered across the chat.

The same video shows Substrate, a research tool by Kay Kumar (not public yet). It reads a chat and draws two maps side by side: what the person meant, and what the model decided. Then it circles the gaps, like the model switching to a formal tone nobody asked for, or quietly changing what a sentence meant.

The fix is to keep the card. Save the decisions as a file (areas/blog/voice.md in my folder), and next time "tighten this paragraph" is right in one go:

long chat (4 rounds) ──► pull out the decisions ──► voice.md
         ▲                                              │
         └──── a new mistake shows up ◄── next request ◄┘

I don't have Substrate, so I use the end-of-session notes from section 2. Their where the AI went its own way heading is my version of the red circles. A week of those, read back, is how I found the corrections in Your corrections are your next rules.

Test: the real check is whether the same correction stops showing up week after week.

5. Separate the model from the system

A restaurant isn't its chef. Most of what makes it work is ordinary: the fridge, the stove, the order tickets, the person who checks each plate before it goes out. Swap the chef and a well-run kitchen still serves the same menu.

AI tools work the same way. The model is one step in the middle. Around it sit plain code, written rules and checks.

request → routing → tools → model → check → result
           code      code    (swap)  person + code

The useful question is: if I changed the model tomorrow, what would still work?

In my setup the answer is almost everything. FirstMate and Kun Chen's tools are the kitchen: separate worktrees, watchers, and a pre-push gate that runs review, tests and lint. The map in AGENTS.md is the written rules. Claude, Codex or Pi is whichever chef is on shift.

The smallest version of this is this post. It sits in my blog room (areas/blog/). The room already knows how I want it to sound (voice.md), how a post is laid out (template.md) and where drafts go. From there, "write the next section" is enough of a prompt, whichever tool I use.

Test: tests/e2e-probe.sh asks four different AI tools the same question. If all four return the canary, the context doesn't depend on which model is on shift.

6. Fix one thing, then rerun

Tuning a guitar: pluck one string, adjust, pluck again. Turn all six pegs at once and you'll never know which one put it out of tune.

Fix these files the same way. When an answer comes back wrong:

read → draft → check against the source → find the one cause → change one line → rerun the same task

Keep the change if it helped. Drop it if it didn't.

Test: the tests follow the same rule. Delete voice.md and rerun tests/run.sh: the checks that need it fail and the rest still pass. One change, one visible effect.

7. How I wired it up

Everything lives in one git repo, my dotfiles:

dotfiles/
├── home.nix          the list of links
├── home/AGENTS.md    the map (every tool reads it)
└── context/          rooms, inbox, tests

Setting up a machine takes three steps: clone the repo, run the rebuild script (it creates every link), run the tests. A normal day looks like this:

start a session    any tool reads the map → routes to a room
work               say feedback as rules
"end of session"   notes land in the inbox's sessions/ folder
daily              backpass proposes rule changes, writes nothing
review             I approve the changes I agree with

FirstMate runs several agents at once. Each picks up the same map through its own tool's link, so there's nothing extra to sync. Each project repo adds its own short AGENTS.md for its build and test rules.

What's still missing: chat apps can't follow links on my disk. These include Claude.ai, Claude Desktop's chat and Gemini on the web. For now I paste the map into a project there. One idea I haven't built: a small MCP server with two tools, "load context" and "save context", so chat apps could read the map and write to the inbox too.

If you take one thing from this post, take this. Write down what you keep explaining. Put it where every tool can find it. Change it only on purpose.
