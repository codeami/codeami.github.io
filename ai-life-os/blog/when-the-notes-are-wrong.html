The problem

In the library post, the card catalogue stands for the AGENTS.md map: one short file that tells the AI which drawer to open. A catalogue is only useful while its cards are true.

This happens to coding agents. Xu and Wu measured it in "Stale Instruction Files Override the Code in Coding Agents: A One-Sentence Fix" (October 2026). They ran 320 runs over 40 Python projects, with Claude Code and Codex CLI, and gave each project an instruction file that conflicted with the code.

  • The file won. 90.1% of choices followed the stale file.
  • Noticing did not help. Claude Code flagged the conflict in 79 of 80 runs and still complied.
  • Some agents rewrote working code. Codex changed code that worked to match the file in 20 of 80 runs, and the tests failed in 17 of those.

The agent did not miss the mismatch. It saw it and chose the card.

1. The idea: let the code win a disagreement

What is the sentence?

The authors added one sentence to the user-level instruction file, the file every project loads. It gives the code precedence and asks for every mismatch to be listed. Mine reads:

The sentence

When docs and code disagree on a fact (a path, name, command, flag or style convention), follow the code and list each mismatch in your final reply. A documented decision or safety rule still wins until I change it.

With it, code-following rose from 4.2% to 91.4%. The rewrites stopped, and the test pass rate went from 89.4% to 100%.

2. Why it happens

Why does the card beat the shelf?

The study's explanation is about how the text arrives. The instruction file reaches the model as an instruction. The code reaches it as tool output, the result of reading a file. Models rank instructions above tool output.

So the order of trust follows the route the text took, and not whether it is true. The sentence works because it is an instruction too. The higher-ranked text now says to prefer the code.

3. Why the rule is scoped

Why not "the code always wins"?

Because the code and the notes hold different kinds of statement.

  • Facts are things the code can answer: a path, a name, a command, a flag, a style convention. If the notes say one and the code shows another, the notes are stale.
  • Decisions and safety rules are things the code cannot answer. "Ask before deleting data" and "never push to the main branch" are choices I made, written down on purpose. If some code breaks one, the code is what needs fixing.

Hence the second half of the sentence: a documented decision or safety rule still wins until I change it. Only I change it, in the file, on purpose.

Why it matters

Notes go stale because work moves. A map file with no wrong cards is rare, and agents act on the wrong ones with full confidence.

The sentence does two jobs. On the day a card is wrong, the agent follows the code, so working code stays. And the list of mismatches in the final reply is a list of cards to fix. The map gets more accurate every time an agent uses it.

4. What's next

  • The sentence stays in my base map, so every tool I use loads it.
  • Every task ends with the mismatch list. I read it and correct the stale card the same day.
  • Decisions and safety rules stay in the file as written, and change only when I change them.

5. Try it yourself

Three steps.

  1. Add the sentence to the instruction file your tool loads for every project.
  2. Give the agent a small task in a project whose notes you know are out of date.
  3. Check that the final reply lists each mismatch. Then fix the cards it names.
